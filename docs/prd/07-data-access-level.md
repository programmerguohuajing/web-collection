# PRD 07：数据访问等级（Data Access Levels）

> 优先级：P2 ｜ 里程碑：M3 ｜ SDK 改动：无
> 修订：2026-08-26 评审修订——pii.js 定性更正（服务端共享模块，非采集端）；白名单制落地方式明确为 handler 注册制；补充当前等级查询端点
> 前置：账号/角色体系立项（决策 D3）——无账号体系时本 PRD 仅落地服务端脱敏硬编码
> 参考：对方「数据访问等级 L1-L4」（L4 可查看完整 IP）与「事件明细」IP 省市/运营商展示

## 1. 背景与问题

- 平台采集 IP、userId、手机号等敏感数据；当前控制台无访问控制，任何能打开页面的人看到同等敏感度数据；
- 合规要求（个保法）与客户安全审计均要求"最小可见"原则；
- 脱敏基建现状（评审核正）：**采集端**脱敏在 SDK 内部（redact/redactObject + privacy.redactKeys，packages/sdk/src/index.js）；[pii.js](../../../packages/ai/pii.js) 是**服务端**共享模块（worker 与 ai-service 共享，海外通道出境前强脱敏）——原稿"已有 pii.js 脱敏基建（采集端脱敏）"混淆了两者。本 PRD 的服务端分级裁剪可直接复用 pii.js 的规则实现；
- 缺的是"存储完整、按角色分级展示"的服务端分级能力。

参考系统实践：数据访问等级 L1~L4，L4 可查看完整 IP，事件明细默认展示 IP 省市/运营商；采集治理页展示当前等级。

## 2. 目标 / 非目标

**目标**
- G1 四级数据访问模型，按账号等级裁剪 API 响应中的敏感字段
- G2 用户链路（01）/事件明细类页面的 IP 双形态展示：归属地（低级）/ 完整 IP（L4）
- G3 L4 敏感操作审计日志
- G4 现有 PII 采集端脱敏策略不变（双保险）

**非目标**
- 不做采集端分级（存储始终含完整数据，分级只发生在展示层——否则低等级用户的数据分析能力受损）
- 不做字段级自定义权限（固定四级，避免配置爆炸）
- 不做数据加密存储（传输 TLS + 库内访问控制已满足当前合规要求，M3 后评估静态加密）

## 3. 等级模型

| 等级 | 角色（示例） | IP | userId/手机号 | 原始事件详情 | 导出 |
|---|---|---|---|---|---|
| L4 完整数据 | 平台管理员 | 完整 IP | 原值 | ✅ | ✅ |
| L3 运维诊断 | 研发 | 段脱敏 `219.145.8.*` + 归属地 | userId 原值 / 手机号脱敏 | ✅ | ✅（脱敏） |
| L2 业务分析 | 产品/运营 | 归属省市 + 运营商 | userId 哈希前 8 位 / 手机号脱敏 | ✅（context 脱敏） | ❌ |
| L1 只读统计 | 外部/演示 | ❌ | ❌ | ❌（仅聚合指标） | ❌ |

- 默认等级：L2（新账号）
- 等级变更：仅 L4 可操作，写入审计

## 4. 用户故事

- 作为平台管理员，给客服开通 L1 账号用于查看告警大盘，确保其无法接触用户明细。
- 作为研发（L3），在用户链路页看到 `IP 219.145.8.*（上海·移动）`，足够定位机房/运营商问题。
- 作为安全审计员，导出近 30 天 L4 完整 IP 查看记录，逐条核对正当性。

## 5. 功能需求

### FR-1 账号与等级管理（依赖账号体系）

- 系统设置 → 成员管理：列表（账号/等级/最后活跃）、邀请/禁用、等级调整
- 等级调整二次确认 + 审计

### FR-2 服务端字段裁剪（核心，无账号体系也先落地）

- 统一脱敏中间件：响应序列化前按请求者等级处理敏感字段白名单：

| 字段路径 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|
| `ip` | 删除 | 删除（保留 ip_region） | 段脱敏 | 原值 |
| `userId` | 删除 | hash8 | 原值 | 原值 |
| `user_phone` | 删除 | `138****1234` | 同左 | 原值 |
| `context.*` 命中 PII 规则 | 删除 | 按 pii.js 规则 | 按 pii.js 规则 | 原值 |

- 实现位置：Node（express 中间件 + 各 handler 出口）与 Worker（route 出口）各一份，规则表共享于 packages/
- **白名单制**：新接口默认全脱敏，显式声明才放行——防新增接口泄漏。落地方式为 **handler/route 注册制**（各出口声明可原值输出的字段路径清单），不做全局响应体扫描（性能与误伤不可控）；字段/正则规则表收敛至 packages/ 共享（与 pii.js 同源），Node 与 Worker 各自接入同一份规则

### FR-3 前端展示适配

- 用户链路节点详情（01）、事件明细类页面：IP 行按等级渲染 `IP(归属地)` / `IP(脱敏)` / 完整 IP，角标显示当前等级
- L1 账号访问明细类页面：整页替换为"当前等级无权查看明细"引导页

### FR-4 审计

- 记录：L4 查看完整 IP 的单条动作（页面 + 目标事件 id + 时间）
- 审计查询：仅 L4 可见；保留 ≥180 天

### FR-5 等级可视化

- 顶栏账号菜单显示当前等级徽标；采集治理页展示"当前数据访问等级"卡（借鉴对方）

## 5. 接口设计

```
GET  /api/me/access-level             → 当前账号等级（新增；前端顶栏徽标与 L1 引导页渲染依赖此端点。无账号体系阶段返回环境变量全局等级）
GET  /api/members                        → 成员列表（L4）
PUT  /api/members/{id}/level             → { level: "L1|L2|L3|L4" }
GET  /api/audit/data-access?start=&end=  → L4 敏感访问审计
```

- 所有既有明细接口响应自动经过 FR-2 中间件，**明细接口**本身不感知等级（业务零改动）；等级仅通过 /api/me/access-level（或并入 /api/capabilities 响应的 accessLevel 字段）显式暴露给前端——否则 L1 引导页与顶栏徽标无从渲染

## 6. 数据模型

```sql
-- 依赖账号体系表（D3）；无账号体系时 FR-2 用环境变量配置全局等级
create table if not exists members (
  id varchar(32) primary key,
  name varchar(64) not null,
  access_level varchar(2) not null default 'L2',
  created_at bigint not null,
  updated_at bigint not null
)
create table if not exists data_access_audit (
  id bigserial primary key,
  member_id varchar(32) not null,
  action varchar(32) not null,          -- view_full_ip | level_change | export
  target varchar(128),
  created_at bigint not null
)
```

## 7. 边界与异常

| 场景 | 行为 |
|---|---|
| 未登录（无账号体系阶段） | 全局等级 = 环境变量 `DATA_ACCESS_LEVEL`（默认 L2） |
| 中间件故障 | fail-close：敏感字段删除态输出，绝不能 fail-open |
| 导出接口 | L2 及以下直接 403 |
| 等级降级即时生效 | 等级随 session 校验（JWT 携带 + 短有效期），不依赖前端缓存 |

## 8. 成功指标

- 敏感字段泄漏面：L2 及以下响应中完整 IP/userId 出现次数 = 0（自动化断言进 CI）
- L4 完整 IP 查看 100% 有审计记录
- 客户安全审计通过（定性）

## 9. 里程碑
