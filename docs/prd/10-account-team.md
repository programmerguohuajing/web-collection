## 0. 一句话定位

从「一把钥匙走天下」的单租户自用模式，建立**最小可用的账号 / 团队 / 角色（RBAC）地基**：能注册登录、能建团队、能邀请成员、能按角色分配权限、能把应用（appId）归属到团队——从而解锁 07 数据访问等级的「按成员授权」，并为 D3 计量计费、D4 白标私有化提供租户载体。

## 1. 产品目标

- **G1 · 有身份**：注册 / 登录 / 会话，管理 / 查询接口 100% 可识别「是谁在调用」。
- **G2 · 有归属**：应用（appId）归属团队，跨团队数据默认不可见。
- **G3 · 有权限**：最小角色集（Owner / Admin / Member / Viewer）覆盖协作场景，且**角色（能做什么）与数据等级（能看多敏感）正交分离**。
- **G4 · 解锁 07**：把 `DATA_ACCESS_LEVEL` 从「全局环境变量」升级为「按成员取值」，等级变更有审计。

## 2. 用户故事

- 作为**平台 Owner**，我希望用邮箱注册并创建团队、把公司 5 个 appId 挂到团队下，以便把过去共享一把钥匙的现状收敛成可管理的协作空间。
- 作为**团队 Admin**，我希望通过邀请链接把研发 / 产品拉进团队并分别给 Member / Viewer 角色，以便新人当天就能看数据、但改不了采集配置。
- 作为**普通 Member**，我希望登录后只看到本团队的应用与告警，并能配置告警规则和远程配置，以便日常排障不被其他团队数据干扰。
- 作为**只读 / 外部 Viewer**，我希望被授予 L1 只读统计等级后能看大盘与告警，以便给客户演示时**不接触任何用户明细**（IP / userId 在 API 层已被裁剪）。
- 作为**安全审计员**，我希望导出近 180 天的成员 / 角色 / 等级变更与敏感访问记录，以便通过客户安全审计。

## 3. 需求池

> P0 = 随首版交付（解锁 07）；P1 = 应做；P2 = 长尾。⚠️ = 依赖后端双栈改造（Node/PG + Cloudflare/D1，需同表同接口同能力位，遵循 `docs/prd/README.md` 原则 #4）。

### P0 · 账号、团队、成员、角色、应用归属 ⚠️
- **FR-1 账号**：邮箱 + 口令注册 / 登录；口令 `argon2id` 加盐哈希，绝不存明文；邮箱唯一（大小写归一）。⚠️
- **FR-2 会话**：登录下发凭据，Cookie `HttpOnly+Secure+SameSite=Lax`；短访问令牌（≤2h）+ 可撤销刷新令牌；登出即失效。⚠️
- **FR-3 引导首个 Owner**：空库首次启动，`ADMIN_API_KEY` 创建第一个 Owner 账号，随后引导关闭 / 降级。⚠️
- **FR-4 团队**：创建 / 编辑（名称 + slug）；用户可属多团队；扁平无嵌套。⚠️
- **FR-5 成员管理**：邀请 / 移除 / 改角色；**不变量：团队必须保留 ≥1 active Owner**，末位 Owner 不可自我降级 / 退出（须先转让）。⚠️
- **FR-6 角色与权限（最小 RBAC）**：固定四角色 `owner/admin/member/viewer`；**任何人不得授予高于自身的角色或数据等级**。⚠️
- **FR-7 应用归属**：`applications` 增加 `team_id`；列表 / 查询按当前团队过滤；**SDK 采集侧零改动**。⚠️
- **FR-8 数据等级挂载**：`team_members.access_level` 沿用 07 的 `L1~L4`；角色派生默认值（Owner→L4/Admin→L3/Member→L2/Viewer→L1）+ Owner 可单独覆盖。⚠️
- **FR-9 与 07 衔接**：`access-service` 改为 `resolveAccessLevel(req)`（已登录取成员等级，未登录 / `accounts=false` 回落环境变量 fail-close L2）；`applyAccessLevel` 中间件与 `packages/access-level.js` 规则**零改动**。⚠️
- **FR-10 越权防护**：所有 `/api/*` 管理接口经身份中间件；跨团队 appId → `403`；未登录 → `401`；采集 / 静态 / 健康检查豁免。⚠️
- **FR-11 能力开关**：`accounts` 能力位进 `NODE_CAPABILITIES` / `WORKER_CAPABILITIES`；前端据此切换「API Key 输入框 / 登录态用户菜单」。⚠️
- **FR-12 迁移**：`members` 表保留不删（兼容 `/api/members`），新写入改走 `team_members`；一次性脚本将登记项写入默认团队（无邮箱者标记「待认领」，不自动生成账号）。⚠️

### P1 · 权限细化、邀请、审计 ⚠️
- **FR-13** 权限矩阵落到共享常量 `packages/rbac.js`（Node 与 Worker 同源，避免漂移）。⚠️
- **FR-14** 邀请链接 + 过期：一次性 token（哈希存储）、默认 7 天过期、可撤销 / 重发；接受时邮箱已注册则直接加入。⚠️
- **FR-15** 操作审计 `audit_logs`（actor / action / target / ip / ua / detail），保留 **≥180 天**（与 07 一致）；仅本团队可见。⚠️
- **FR-16** 登录安全：失败限流（5 次 / 15 分钟 / 邮箱+IP）、弱口令校验、会话列表与「踢下线」。⚠️
- **FR-17** 账号自助：改口令、退出失效全部会话、资料变更需口令确认。
- **FR-18** 成员活跃与席位视图：`last_active_at` 落库，团队页展示近 30 天活跃数（只计数，不计量不计费——计费属 D3）。

### P2 · 企业级身份与隔离
- **FR-19** SSO（OIDC / SAML）+ 域名自动加入（需 D4 白标配合）。
- **FR-20** SCIM 用户 / 组自动开通回收。
- **FR-21** 多租户隔离增强：团队级分区 / 独立库、租户级配置与白标载体（与 D4 合并设计）。⚠️
- **FR-22** 自定义角色 / 应用级（per-appId）角色覆盖。
- **FR-23** MFA（TOTP / WebAuthn），L4 成员可强制。

## 4. 与现有 access-levels 的合并设计要点（07 如何挂在账号 / 团队上）

- **现状核实**：`access-service.currentAccessLevel()` 读环境变量 `DATA_ACCESS_LEVEL`（全局，fail-close L2）；`/access-levels` 页「＋ 登记成员」仅填名字，`members` 表无邮箱 / 无身份 / 无法登录（见 `009...` 及代码核实）。
- **角色与等级正交**：角色决定「能做什么」（权限矩阵），`access_level` 决定「能看 L1~L4 多少」（沿用 07 四级模型），两者共同构成一次请求授权判定。
- **等级挂人**：`team_members.access_level`（默认由角色派生，Owner 可单独覆盖）。
- **07 裁剪零改动**：`access-service` 仅把入参从「全局常量」换成「请求者等级」；`applyAccessLevel` 中间件与 `packages/access-level.js` 裁剪规则**零改动**。
- **页面合并（不并列）**：新增 `/teams` 承接成员列表 + 等级调整 + 审计；`/access-levels` **降级为只读说明页**（保留 L1~L4 能力矩阵 +「我的当前等级」徽标），移除「＋ 登记成员」写入入口；路由保留至少一个大版本避免书签失效。侧边导航改名为「团队与成员」。
- **依赖顺序**：本 PRD P0 → 07 M3-b（按成员授权）；07 M3-a（服务端裁剪中间件）可与本 PRD 并行。

## 5. 待确认问题（Open Questions）

- **Q1 鉴权方式**：自研最小账号体系（本 PRD 默认：邮箱 + 口令）vs 接入现有 / 第三方鉴权？建议自研，SSO 留 P2（FR-19）。
- **Q2 数据隔离级别**：D1 多租户仅靠 `appId/teamId` 行级隔离（`team_id` 过滤 + 401/403 中间件）是否够？还是需独立库 / 分区？建议本期**行级隔离**，独立库留 P2（FR-21）。
- **Q3 迁移路径**：存量单租户数据（`members` 登记项、`applications.owner` 自由文本）如何迁移？建议：`members` 不删、标记 deprecated，一次性脚本迁登记项入「默认团队」（首位 Owner 自动建）；无邮箱者标记「待认领」、不自动生成账号；`applications.owner` 列保留不动，新增 `team_id` 默认团队约束。
- **Q4 能力开关默认值**：`accounts` 能力位默认 `false`（存量自托管零破坏）还是 `true`（新部署）？建议 `false` 默认、显式开启；`ADMIN_API_KEY` 保留为 `ALLOW_ADMIN_API_KEY`（M-a 默认 true → M-b 默认 false，仅用于引导 / CI）。
- **Q5 双后端同批**：Node(PG) 与 Cloudflare(D1) 是否同批交付？建议 Node 先行、Worker 同批跟进；不同批时能力位**必须报 `accounts=false`**（原则 #4 双后端一致，绝不上报未实现能力）。

## 6. 粗略里程碑（M 系列，不含具体日期）

- **M1 地基（P0 后端核心）**：账号 / 会话 / 团队 / 成员 / RBAC 数据模型（双栈迁移脚本）+ 身份中间件 + 与 07 衔接（`resolveAccessLevel`）。出口：`/api/*` 管理接口 100% 经身份中间件、跨团队 403、未登录 401（CI 断言）。⚠️
- **M2 协作（P1 主体）**：邀请链接、审计日志、登录安全、账号自助、`/teams` 前端页与顶栏登录态、`/access-levels` 降级。出口：邀请 7 日接受率 ≥70%、活跃团队比例（上线 1 月）≥50%。⚠️
- **M3 解锁 07**：本 PRD P0 之后一个迭代内落地 07 FR-1/3/4/5（按成员授权 + 等级变更审计）；与 07 M3-a 并行。
- **M4 长尾（P2）**：SSO / SCIM / MFA / 自定义角色 / 多租户隔离增强（与 D3 计量、D4 白标衔接）。⚠️

## 7. 双栈改造标注汇总

- **依赖后端双栈（Node/PG + Cloudflare/D1）**：FR-1~12、FR-13~16、FR-21、M1/M2/M4 全部数据模型、接口、身份中间件、审计、与 07 衔接；须同表同接口同能力位（原则 #4）。
- **前端（受 `accounts` 能力位控制）**：新增 `/teams`、`/login`、顶栏登录态切换、`/access-levels` 降级。
- **零改动**：SDK 采集逻辑、`COLLECT_TOKEN` / `x-app-key` 写入通道、07 的四级模型与 `packages/access-level.js` 裁剪规则。
