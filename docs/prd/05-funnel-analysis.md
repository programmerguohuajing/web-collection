# PRD 05：漏斗分析（Funnel Analysis）

> 优先级：P1 ｜ 里程碑：M2 ｜ SDK 改动：无
> 修订：2026-08-26 评审重大修订——系统已存在双端漏斗功能与 funnel_definitions 表，本 PRD 定位由「新建」改为「增强既有」，接口/数据模型全面对齐现状
> 参考：对方「交易漏斗」（业务定制：trade 事件序列）——本设计泛化为自定义漏斗
> 关联：依赖统一事件口径（上位 P0）；与 01 用户链路、02 事件字典打通

## 1. 背景与问题

- 我们有自动路径分析（PathsPage，描述"用户实际怎么走"），但无法回答"设计的转化流程表现如何"——路径分析是探索型的，漏斗是验证型的，两者互补；
- 参考系统的交易漏斗证明了业务价值（成交价区间、订单数、缺失金额订单），但其漏斗是硬编码业务事件，无法复用到注册、表单等其他流程。

**现状盘点（2026-08-26 评审核实，本 PRD 出发点由此修正）**：

- 系统**已具备基础漏斗能力**：Node 与 Worker 双端均有 `/api/funnels` 列表/保存/删除/运行接口（apps/api/src/index.js:283-286；cloudflare/worker.js:231-234），前端 capabilities 已声明 `funnels: true`；
- 存储为 `funnel_definitions` 表（name / app_id / steps_json / window_ms 列齐备；早期 `funnels` 表已幂等迁移至该表名——**本 PRD 不得再新建 funnels 表**，避免重蹈表名迁移）；
- saveFunnel 语义为 POST 带 id 即更新（analytics-service.js:467）；
- 既有能力的差距：无步骤属性约束、无细分维度、无转化趋势、无流失洞察闭环、无模板——这些正是本 PRD 的增量范围，编辑器交互需先核对现有前端入口再定承接方式。

## 2. 目标 / 非目标

**目标**
- G1 任意 2~6 个事件序列自定义漏斗，支持步骤级属性约束
- G2 转化率报告：总转化、各步转化/流失、按维度（浏览器/平台/版本）细分对比
- G3 流失洞察闭环：流失样本一键跳转用户链路（01），AI 交叉分析"流失用户中多少遇到了错误"
- G4 预置常用模板：注册转化、下单转化、表单完成

**非目标**
- 不做实时漏斗（小时级延迟可接受，预聚合）
- 不做多漏斗对比（M3 评估）
- 不支持乱序漏斗/并行路径（严格时序，窗口内按序匹配）

## 3. 用户故事

- 作为产品经理，建「浏览商品 → 加入购物车 → 提交订单 → 支付成功」漏斗，发现第 2→3 步转化仅 31%，按浏览器细分发现 Safari 只有 9%，点"流失用户链路"抽样看到 Safari 用户点击被遮挡元素无响应，转研发。
- 作为运营，用注册漏斗模板监控每周转化趋势，周报引用。

## 4. 功能需求

### FR-1 漏斗列表

- 列：名称、步骤数、近 7 日总转化率（迷你趋势）、创建人、更新时间
- 操作：新建 / 编辑 / 复制 / 删除（仅创建人与管理员）
- 预置模板卡片（首次进入展示）：注册转化、下单转化、表单完成——一键套用后改事件即可

### FR-2 漏斗编辑器（抽屉向导）

| 字段 | 规则 |
|---|---|
| 名称 | 必填，≤40 字 |
| 步骤 | 2~6 步；每步选事件（下拉，数据源=02 事件字典，支持搜索）+ 可选属性约束（key=value，最多 2 条/步） |
| 转化窗口 | 30 分钟 / 1h / 24h / 7d（单选） |
| 细分维度 | 无 / 浏览器 / 平台 / SDK 版本 / App 版本（单选） |

- 步骤事件下拉直接展示字典健康状态，🔴 停滞事件标灰提示"该事件近 7 日无上报"

### FR-3 漏斗报告

```
[口径说明条] 用户按 user_id 去重；步骤须在窗口内按时间严格递增匹配；
            属性约束取事件 context 字段；区间 = 近 7 天（可选）

┌ 总览卡 ────────────────────────────────────┐
│ 进入用户 12,033 │ 总转化 12.4% │ 平均转化耗时 8m32s │
└───────────────────────────────────────────┘
[漏斗图] 步骤横向条形：每步人数/转化率/相对上步流失数
[趋势图] 总转化率按日曲线（近 30 天）
[细分表]（选了维度时）每行一个维度值 × 各步转化率；异常行高亮
[流失洞察]
  · "流失用户中 31% 在步骤 2~3 间遇到 JS 错误"（errors 关联查询）
  · [查看流失用户链路 →] 抽样 20 个流失会话跳 01 用户链路
  · [AI 分析流失原因 →] 摘要喂 diagnoser
```

### FR-4 权限

- 创建/编辑/删除：创建人 + 管理员；查看：所有登录用户

## 5. 接口设计

```

GET  /api/funnels                    → 列表（沿用既有）
DELETE /api/funnels/{id}             → 删除（沿用既有）
GET  /api/funnels/{id}/report?start=&end=&dimension=   → 报告（新增；steps_json 扩展 filters 后旧 run 逻辑兼容）

// 兼容约定：不引入 PUT；路径对齐既有双端实现（apps/api/src/index.js 与 cloudflare/worker.js 路由处同步扩展）。
// 既有 GET /{id}/run 作为轻量执行入口保留一个版本周期后收敛到 report，避免双口径。
```

## 6. 数据模型

```sql
-- 复用既有 funnel_definitions（勿新建 funnels 表——该表名历史上已迁移废弃过一次，见 db.js 迁移注释）
alter table funnel_definitions add column if not exists created_by varchar(64);
alter table funnel_definitions add column if not exists dimension varchar(32);
-- window_ms 列已存在；steps_json 结构扩展为 [{event, filters:[{k,v}]}]，存量数据无 filters 视为无约束
-- D1 方言：jsonb → TEXT(JSON)；id 为 integer 自增（既有），接口层 id 保持 number 类型
```

- 存量行 created_by 为空：列表显示"—"，编辑权限归管理员
- 计算引擎 M1：原始 events 扫描（限制单次查询 ≤7 天 × 单应用，超限拒绝并提示预聚合未就绪）
- M2：接入日粒度 user-event 预聚合表（`user_event_daily(user_hash, day, event, count, first_ts, last_ts)`）后支持 30 天区间
- 时序匹配算法在服务端执行（Node 与 Worker 同一份逻辑，放 packages/）

## 7. 边界与异常

| 场景 | 行为 |
|---|---|
| 步骤事件无数据 | 报告该步人数 0，提示核对事件名与字典健康状态 |
| 区间数据量超限 | 明确报错"该区间数据量过大，请缩短范围"，不降级假数据 |
| user_id 缺失（匿名） | 按 device_id 兜底去重，口径注明 |
| 漏斗被删除后历史链接 | 报告页提示"漏斗已删除" |
| 属性约束字段不存在 | 该步人数按 0 计，报告标注"约束字段无数据" |

## 8. 成功指标

- 上线 1 个月：创建漏斗 ≥5 个、周活跃查看 ≥3 次
- 流失洞察 → 用户链路跳转率 ≥30%（与 01 联动成立）
- 通过漏斗发现的可行动问题数（定性收集）

## 9. 里程碑

M2-a 编辑器 + 报告（7 天窗口）；M2-b 细分维度 + 流失洞察 + 模板；M3 长区间预聚合。
